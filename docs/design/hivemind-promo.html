不造引擎，造蜂群。 Don't build another agent. Build the hive.

凌晨三点，五个人对着同一个 pod 翻日志，每个人都在重跑同一条 kubectl——没人知道隔壁已经查过了。Hivemind 解决的就是这件事：不是 agent 不够聪明，是团队里的 agent 没有共享思考的那一层。它不替你判根因，只保证证据别丢、重复查询合并、写动作得有人点确认。 3am. Five engineers paging through the same pod, each re-running the same kubectl because nobody sees the person next to them already did. That's the actual problem — not "agents aren't smart enough," but that the agents on your team share no substrate for thinking together. Hivemind doesn't call the root cause. It just makes sure evidence survives, duplicate reads coalesce, and no write happens without a human clicking confirm.

我们解决什么问题THE PROBLEM

问题不在 agent 够不够聪明The bottleneck isn't agent intelligence

每个工程师桌上的本地 agent 都挺好用。疼的是它们各跑各的——四次故障、四个终端、四份互相矛盾的结论，没人记下来，下次还得重来。Every engineer's local agent works fine. The pain is they run blind to each other — four incidents, four terminals, four contradictory answers, none of it written down, all of it redone next time.

01

同样的查询，五个人各跑一遍The same query, five times

每个本地 agent 都在重复执行几乎相同的 kubectl / 日志查询。Token 和时间成倍烧掉，还互相看不到。Every local agent re-runs nearly identical queries. Tokens and time burn in parallel — and nobody sees anybody.

02

结论互相矛盾，没有共同事实No shared ground truth

A 说缓存问题，B 说连接池耗尽。没有共享的证据层，谁也无法说服谁，只能靠嗓门。A says cache; B says connection-pool exhaustion. Without a shared evidence layer, nobody can convince anybody.

03

排过的障，下次重来Every incident is the first time

事故结束后知识死在个人会话里，团队知识库永远是空转。冷启动一次比一次贵。Knowledge dies in personal sessions. The team's memory stays empty, and every cold start costs more.

04

只有建议，没有可审计的决策Advice without accountability

工具给"AI 建议"，决策责任却永远甩给疲惫的 on-call 工程师——没有任何可审计的记录。Tools hand out AI suggestions, but the decision burden lands on a tired on-call engineer — with zero auditable trail.

所以这件事不是"造个更聪明的 agent"。是给已经存在的那些 agent，补上那层缺失的基础设施——让证据活得过这次会话、让重复的查询合并、让写动作要有人点头。我们不造引擎，我们造蜂巢。 So this isn't "build a smarter agent." It's giving the agents you already run the one layer they're missing — evidence that outlives the session, reads that coalesce, writes that need a human's nod. We don't build engines. We build the hive.

四大支柱FOUR PILLARS

四条反直觉的坚持Four counter-intuitive commitments

这四条都不是流行做法。每条都对应我们踩过的一个坑——所以宁可笨一点，也不要那个坑再发生。None of these is the fashionable choice. Each one maps to a specific hole we fell into and don't intend to fall into again — so we'd rather be a bit dumber than re-dig that pit.

01 / COLLABORATION
证据先于聊天Evidence before chat
讨论可以无限，事实层必须有界。agent 可以各执一词，但只有结构化证据与决策改变事故状态。Chat can be infinite; the fact layer must have bounds. Agents may argue forever, but only structured evidence and decisions change incident state.
PMA 协议：提案 → 合并 → 仲裁PMA: Propose → Merge → Adjudicate 聊天不进事实层Chat never enters the fact layer 确定性裁决器只做协调Deterministic adjudicators only coordinate 根因真假归人裁决Root-cause truth belongs to humans
反直觉：我们不建"agent 聊天室"——最便宜的讨论，是最不可靠的证据。Counter-intuitive: We don't build "agent chat rooms" — the cheapest conversation is the least reliable evidence.
02 / DEDUPLICATION
查询级去重Query-level dedup
一次查询，全队受益。去重不是"大家别重复"的口号，而是操作指纹这个粒度上的硬机制。One query, the whole team benefits. Dedup isn't a slogan — it's a hard mechanism at the granularity of an operation fingerprint.
操作指纹 → single-flight 合并Operation fingerprints → single-flight 重复 409 → 转验证副本Duplicate 409 → verification copy 咨询性租约，不是排他锁Advisory leases, not exclusive locks 血缘 DAG 计算证据独立性Lineage-DAG evidence independence
反直觉：排障不是互斥写入——目标是无意重复最小化 + 受控冗余交叉验证，不是"重复归零"。Counter-intuitive: Troubleshooting isn't mutual exclusion — we minimize unintentional duplication while keeping controlled redundant cross-checks.
03 / DISTILLATION
发生过 ≠ 可复用Happened ≠ reusable
事故中只产候选，事故后认证。一次成功不能自动成为知识——防的是 LLM 一本正经地写错 runbook。Candidates during the fire, certification after. One success doesn't auto-publish knowledge — that's how confident-but-wrong runbooks happen.
双流水线（事件中 / 事件后）Two pipelines: in-incident / post-incident 认证链 candidate→verified→certified→revokedCertification chain: candidate→verified→certified→revoked 失效由依赖 / 失败率 / 反例驱动Invalidation by deps, failure rates, counter-evidence
反直觉：LLM 只写候选；编译、策略、测试决定发布。认证之外的知识不浮出。Counter-intuitive: LLMs propose; compilers, policies and tests dispose. Uncertified knowledge never surfaces.
04 / RECOVERY
写操作永远人审Humans own the write path
AI 定位，人拍板，机器执行必须有证据。恢复不是 AI 的自由发挥，而是 IC 决策的受控执行。AI diagnoses, humans decide, execution requires evidence. Recovery is not AI improvisation — it's controlled execution of an IC decision.
证据门禁：无假设 → 拒绝动作Evidence gate: no hypothesis → no action 强类型动作 + 默认 dry-runTyped actions + dry-run by default 无威胁模型不进写路径No write path without a threat model
反直觉：我们公开拒绝"全自动修复"叙事——P0 干脆没有写路径。Counter-intuitive: We openly refuse the "fully autonomous healing" narrative — P0 ships with no write path at all.
我们不做什么WHAT WE REFUSE TO DO

四条铁律Four iron rules

✕ 我们不造 agent 引擎

复用，不重造Reuse, don't rebuild

复用本地 Claude Code / Codex，平台只是薄 MCP 适配器。你的 agent 零迁移进场。Reuse local Claude Code / Codex; the platform is a thin MCP adapter. Your agents join with zero migration.

✕ 不做"全自主专家团"

默认受 IC 约束IC-gated by default

不借鉴全自主 agent 群演——所有 agent 默认受 IC + PMA + 证据门控约束。No autonomous expert swarms — all agents run under IC + PMA + evidence gates by default.

✕ 不让 LLM 直接发布知识

候选必须过认证链Candidates need a chain

LLM 只生成候选，编译 / 策略 / 测试决定发布。认证链之外的知识永不浮出。LLMs generate candidates; compilers, policies and tests dispose. Nothing surfaces outside the certification chain.

✕ 不在无威胁模型处开放写路径

P0 只读P0 is read-only

没有威胁模型就没有写路径。P0 是只读协同账本——先证明协同，再谈执行。No threat model, no write path. P0 is a read-only collaboration ledger — prove coordination before execution.

不是 PPTNOT A SLIDEDECK

三个闭环，已在本机跑通Three loops, verified end-to-end

真实阿里云告警 → 自动开独立会议室 → GLM-5.2 诊断真实 SLS 日志 → 假设进入矩阵 → IC 裁决。每一步都有迹可查。Real Aliyun alert → auto-created incident room → GLM-5.2 diagnosis of real SLS logs → hypothesis matrix → IC verdict. Every step traceable.

✓ 故障定位闭环Diagnosis loop

真实告警 → 全链路定位Alert to root-cause candidates

告警指纹聚合自动开房，无头调查员读取真实 SLS 日志，LLM 产出结构化假设与反证。Alert fingerprints auto-create the room; a headless investigator reads real SLS logs; the LLM produces structured hypotheses and counter-evidence.

证据链Trail: alert → incident → evidence → hypothesis → IC
✓ 知识蒸馏闭环Distillation loop

事故 → runbook → 秒级召回Incident → runbook → instant recall

distiller 生成候选，IC 认证为 certified；同类新事故按症状指纹召回，命中分数全量计算。The distiller drafts candidates; the IC certifies; similar new incidents recall by symptom fingerprint with full scoring.

证据链Trail: incident → distill → certified → recall (score 1)
✓ 恢复闭环（最小版）Recovery loop (minimal)

证据门禁 + 人审 + dry-runEvidence gate + human approval + dry-run

无假设时动作被拒；IC 批准后默认 dry-run，只展示将执行的命令，不产生副作用。Actions are rejected without hypotheses; after IC approval, execution defaults to dry-run — showing the command, causing no side effects.

证据链Trail: 拒绝 → IC 批准 → DRY-RUN
