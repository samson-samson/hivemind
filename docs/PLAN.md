# Hivemind 产品方案 PLAN

> 版本：2026-08-17 · 定位：开源 AIOps 平台（多智能体协同排障）· 状态：P0 大部完成

---

## 1. 智能运维理念（AIOps Philosophy）

**一句话**：把"N 个工程师 × N 个本地 agent 各查各的故障"，变成"一个互相感知、去重、持续蒸馏、可视化指挥的分布式排障蜂群"。

四条铁律（决定一切设计）：

1. **排障不是互斥写入**——协同目标是"无意重复最小化 + 受控冗余交叉验证"，刻意保留 10-20% 独立复核比零重复更安全。
2. **发生过 ≠ 可复用**——事故中只产候选，事故后认证；LLM 只生成，编译/策略/测试决定发布。
3. **聊天不进事实层**——只有结构化证据与决策改变事故状态（防噪声/防级联幻觉）。
4. **AI 定位，IC 决策**——AI 做根因定位与辅助分析；止血/修复由人类 Incident Commander 拍板，AI 永不自动执行写操作。

**一个指纹 = 一个故障 = 一间会议室**：告警按指纹自动开房，同指纹归并、异指纹隔离，每间房独立讨论。

## 2. 全新的交互（New Interaction）

### 会议室（默认主视图，一个故障一屏）

```
┌──────────────────────────────────────────────────────┐
│ [P1] payment-gateway 5xx 飙升 │ IC 事实1 未解2 去重50% 决策39m │
├──────────┬──────────────────────┬───────────────────┤
│ 与会Agent │  协同诊断流（会议纪要）    │ 根因假设（置信度排行）  │
│ ●explorer│  ▸领取任务 agent-x      │ [85%] 连接池变更    │
│  在查2个  │  ▸提交证据 agent-x      │ [55%] AI诊断:死锁   │
│ ●verifier│  ▸提出假设 headless-    │ [25%] AI诊断:调度   │
│  ●skeptic│    diagnoser          │ [15%] 慢查询(反证)  │
│          │  ▸IC 指示 张倩          │ ────────────────── │
│          │                        │ 🤖 触发 AI 诊断     │
│          │                        │ [IC 发言框] 发布指示  │
└──────────┴──────────────────────┴───────────────────┘
```

**核心交互**（都经过实测）：
- **一键 AI 诊断**：点按钮 → headless-diagnoser 进场 → 读真实日志 → GLM-5.2 假设进面板（1-3 分钟）
- **IC 发言**：输入框发布指示，agent 只读不回复
- **上下文飞轮**：事实收敛进度可视（已确认事实 / 未解问题 / 去重率 / 决策延迟）
- 导航收敛为 4 项（会议室/工作图/证据血缘/IC 操作），其余深层路由保留

### 决策边界提示

假设面板琥珀色提示："AI 仅做根因定位与辅助分析；止血/修复方案由 IC 决策"——把"人最后拍板"做成可见的产品语言。

## 4. 卖点（Selling Points）

1. **不拥有 agent，拥有协同与知识**——复用每个人的 Claude Code/Codex/swarm，平台只做引擎之上的协同层（vs PagerDuty/Datadog 服务端替你查）。
2. **排障即知识库**——每起事故的排查轨迹实时蒸馏，下次同类故障秒级给已验证方案（vs 全行业复盘后慢反馈）。
3. **会议室协同**——每个故障一间房，谁在查什么一目了然，查询级去重省 token。
4. **AI 定位、人决策**——既享受 AI 效率，又守住安全底线（行业 agentic 产品全在往"人审"收敛，我们天生如此）。
5. **云中立、低成本接入**——版本化 capability + 四档接入，阿里云为第一实现。
6. **开源 + 可私有化**——三方模型分工的开发模式本身就可复制。

## 5. 能解决什么问题（Problems Solved）

| 痛点 | 现状（无 Hivemind） | Hivemind 解决 |
|---|---|---|
| 重复排障 | 10 人 10 agent 跑同一批命令 | 查询级 single-flight + 会议室可见 |
| 冷启动 | 每起事故从头查 | 指纹召回 + 知识蒸馏 |
| 排障黑盒 | 不知道谁在查什么 | 会议室全可视化 |
| 幻觉根因 | agent 编根因、从众放大 | 证据门控 + 血缘独立性 + 结论隔离 |
| 处置混乱 | 告警堆叠、无人负责 | 一指纹一房间 + IC 唯一决策 |
| 知识流失 | 复盘没人读 | 实时蒸馏 + 认证 runbook |

## 6. 自动化定位/恢复能力（Automation: Localize & Recover）

### ✅ 定位（已跑通，全部实测）

```
告警 → 自动开房（指纹聚合）
  → 自动诊断（GLM-5.2 读真实 SLS 日志）
  → 分层假设（置信度 + 证据 + 自我反驳）
  → 会议室呈现 → IC 决策
```

实测证据：对真实 sglang 推理故障，AI 给出"worker 死锁 0.72 / GPU 硬件 0.45 / KV cache 0.38 / OTel 0.15"，并自动排除跨集群误关联告警。

### 🚧 恢复（设计完成，P3 落地，诚实边界）

```
AI 提候选（recommended_actions 分级：mitigate/verify/fix × low/medium/high）
  → 护栏引擎（变更窗口/黑名单/爆炸半径）
  → dry-run → IC 审批（双人）→ typed action 执行 → SLO 验证 → 回滚
  → Chaos 复验（提供支持证据）
```

**为什么恢复不能现在全自动**：威胁模型（§9）未完整落地前，写路径不开；且行业教训（AWS Kiro 事故）证明越权自动执行比故障本身危险。P3 只做**单 K8s 环境、强类型、可回滚**的动作。
