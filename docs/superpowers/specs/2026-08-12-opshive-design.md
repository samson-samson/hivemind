# OpsHive（运维蜂巢）设计方案

> 日期：2026-08-12 · 版本：v3（+Agent Swarms 内部通信 + 开源化）· 状态：已获批准（方案 B · Go+Python+TS · 中文优先 · 开源）
> 定位：开源项目 + 参考实现，云中立，**阿里云为第一实现**。

---

## 1. 背景与问题定义

### 1.1 现状痛点

企业中多名工程师各自在本机运行 Claude Code / Codex / Cline 等本地 AI agent。当一次故障发生时：

- 所有人和所有 agent 同时扑向同一套云控制台，跑同样的 `kubectl get pods`、同样的日志 grep，产出相同的根因假设；
- 每个人的排查轨迹互相不可见 → 重复劳动、互相踩踏、浪费 token；
- 每次事故都是一次"冷启动"——上次验证过的结论没有沉淀，下次全员重新查一遍；
- 复盘(postmortem)是事后慢反馈，写出来没人读。

### 1.2 上一版失败教训（aievo `samson` 分支）

aievo 的教训是**再造了一个被商品化的 agent 引擎**（ReAct + 并发工具调度 + SOP 状态机），七成例子是游戏/写作场景，未接任何运维域数据，单机无记忆无协同。**结论：不再自研 agent 运行时。**

### 1.3 设计立场

> 每个工程师本地的 Claude Code / Codex 是现成的算力。**平台不拥有 agent，平台拥有"协同与知识"**——把 N 个私有的排障会话，变成一个互相感知、去重、持续蒸馏、可视化指挥的分布式排障大脑。

### 1.4 两条铁律（来自 Codex 审查）

1. **排障不是互斥写入，是并行探索**——协同的目标不是"重复归零"，而是"无意重复最小化 + 受控冗余交叉验证"。高风险事故中刻意保留 10-20% 的独立复核，比零重复更安全。
2. **发生过 ≠ 可复用，接口通 ≠ 生产可运营**——所有知识沉淀必须区分"事故中候选"与"事故后认证"；所有接入成熟度必须分级验证。

## 2. 目标与非目标

### 2.1 目标（四大支柱）

| # | 支柱 | 核心价值 |
|---|---|---|
| P1 | 全局去重与协同 | N 人 × N 本地 agent 查同一事故：**无意重复最小化**，高风险结论受控双路验证，可分工接力 |
| P2 | 故障知识沉淀 | 排障过程**实时产候选**，事故后**认证**为可复用 runbook（区分"发生"与"可复用"） |
| P3 | 实时协同可视化 | 指挥室视图：工作图 + 因果图 + 证据血缘 + 时间线 + 知识面板 |
| P4 | 修复闭环 | 证据门控 + 强类型动作 + 护栏 + 人审 + 混沌复验（提供支持证据） |

### 2.2 非目标（显式不做）

- **不造 agent 运行时**——复用本地 Claude Code / Codex / Cline，平台只做薄 MCP 适配器。
- **不做告警/监控产品**——告警与监控交给 SLS/ARMS/Prometheus，平台消费事件。
- **不做数据采集 agent**——采集交给 OTEL / iLogtail，平台标准化接入。
- **不承诺全自动修复**——写操作永远人审，P4 是"护栏内的半自动闭环"。
- **不承诺"零重复劳动""一张 YAML 一天接入"**——这些是口号，会让团队为兑现口号而扭曲系统设计。

## 4. 数据模型：Incident Object Model（IOM）

图是第一公民。所有节点带 `confidence / source_agent / timestamp / proof_trace`（proof_trace 指向证据总线上的原始轨迹，可回放）。

### 4.1 节点类型

| 节点 | 含义 | 关键属性 |
|---|---|---|
| `Incident` | 一次事故 | 指纹、状态、负责人、时间窗、关联告警集 |
| `Service` | 受影响服务 | 业务语义（行业短板：都缺业务语义，来源见 §9.5） |
| `Entity` | 实例/Pod/DB/变更/配置 | 云资源 ID、类型、归属 |
| `Symptom` | 观测到的异常 | 来源(指标/日志/告警)、严重度 |
| `WorkNode` | 一个调查工作单元 | `question + scope + expected_evidence + cost + deadline`，负责人 |
| `Operation` | 一次查询/操作 | **操作指纹**（目标+数据源+时间窗+查询AST+过滤+租户+工具版本+数据快照） |
| `Evidence` | 一条排查证据 | 来源 Operation、血缘 DAG、结果、结论、独立性评分 |
| `Fact` | 已确认事实（非假设） | 证据链闭合、多源确认、可引用 |
| `Hypothesis` | 根因假设 | 支持/反对证据、独立性权重、置信度 |
| `RootCause` | 已定根因 | 命名根因 + 传播路径 + 作用机制，人确认 |
| `Action` | 修复/止血动作 | 强类型、审批态、执行态、回滚态 |
| `Runbook` | 认证后的可执行方案 | 类型化字段、验证态、认证链、失效条件 |
| `Guidance` | 人的指示（IC 发言） | 发布者、优先级、不要求 agent 回复 |
| `Capability` | 环境能力描述 | 版本化 descriptor（见 §11.2） |

### 4.2 边类型

`has_symptom · involves_entity · supports / refutes(→Hypothesis) · causes · fixed_by · produced(Runbook) · validated_by(Chaos) · similar_to(历史Incident) · executes(→Operation) · derived_from(证据血缘) · decides(→WorkNode)`

### 4.3 事故指纹

症状签名（告警名 + 受影响实体 + 指标变化模式 + 日志关键词）经规范化哈希，用于**跨事故相似召回**。指纹命中只用于**候选召回**，不直接决定根因。

## 5. 核心协议（平台护城河，开源贡献点）

### 5.1 协同协议（P1）

将"agent 舰队"视为**协调对象**而非分布式共识系统。平台是协调、溯源、决策支持层。

- **工作图（work graph）**：人类 Incident Commander（IC）维护目标与决策权；系统生成可调整的调查工作图。工作单元 = `question + scope + expected_evidence + cost + deadline`（不是 `entity × hypothesis`）。
- **咨询性租约（advisory lease）**：`claim` 不独占；指定验证者可并行复核；**高风险结论强制双路独立验证**（受控冗余）。租约掉线释放，晚到结果**标记为 stale 不污染**当前事故。
- **查询协调器**：查询前生成**操作指纹**；完全相同查询 **single-flight**（并发合并）；兼容查询复用已有结果；需新鲜度才允许重查。
- **角色分工**：探索者 / 验证者 / 怀疑者 / 执行者。不让所有 agent 竞争同一个"根因排名"。
- **check-in / heartbeat**：登记身份（人负责制），心跳续约。

### 5.2 蒸馏协议（P2）——两条流水线

**事故中实时（只产候选，不发布）**：
1. 产出 episode summary、时间线、**候选**诊断步骤、**候选**止血动作；
2. 候选全部标 `provisional`，不进入任何自动执行。

**事故后认证（决定可复用性）**：
1. 基于根因确认 + 变更审计 + 恢复指标生成**类型化、版本化 runbook**；
2. 过验证门禁：静态检查 → 策略检查 → 历史轨迹 replay → 测试环境/canary → 人工 owner 审核；
3. **LLM 只生成候选；编译器、策略引擎、测试决定能否发布。** 生产事故成功只提供一条支持证据，不自动完成认证。

**runbook 类型化字段**：适用范围与排除条件 · 前置条件与权限 · 参数 schema · 诊断步骤 · 止血/修复/验证三类动作 · 幂等性/超时/并发约束 · 爆炸半径 · 回滚或补偿动作 · 成功/失败判定 · 依赖版本与 owner · 来源事故与反例。

### 5.3 修复协议（P4）

1. **证据门控**：无证据链支撑的根因，不允许进入修复流程（防编造根因——行业通病）；
2. **强类型动作**：修复走 typed resource operation（schema/幂等/dry-run/回滚/最大作用域），**`run_command` 不做普通路径**（只作审计受限的兜底）；
3. **护栏引擎**（确定性规则，LLM 只提方案）：变更窗口、命令黑名单、爆炸半径估算、权限校验；
4. 流程：`dry-run → 人审（双人/职责分离）→ 执行（STS 最小权限）→ SLO 验证 → 不达标自动回滚`；
5. **混沌复验**：ChaosBlade 注入重放本次事故，**提供支持证据，不构成证明**（当次成功可能是自然恢复）。

### 5.4 协商协议（PMA：Propose-Merge-Adjudicate，v2）

**核心立场：把"讨论"重构为"提交"，但聊天不进事实层。** 保留受限协作通道（人-人、自由文本观察/业务背景/未知实体/协调意图），但**只有结构化证据和决策能改变事故状态**。心智模型 = 事故图是 Git 仓库，提案是 PR，冲突走"代码评审式仲裁"。规则：**证据发声，规则裁决协调，人裁决真相。**

**Propose**：想表达结论必须提交 `{topic, evidence_chain, confidence, proof_trace, lease_token}`；无证据链的"我觉得"协议层拒绝。提案指纹化 `hash(topic×evidence×data_source)`。

**Merge（决策支持排序，非"确定性共识"）**，输出**不是单一置信分**，而是：
- 已确认事实（`Fact` 集）；
- 有支持的假设（按**血缘独立性**排序：独立性按采集链路/权限域/底层数据源计算，**同一数据源的重复观测不叠加**）；
- 冲突证据（矛盾未决项）；
- 未知项（盲区显式列出）；
- 下一项信息价值最高的调查动作；
- 当前止血决策及责任人。

**Adjudicate（仲裁）**：只由**数据冲突**触发（同点矛盾证据 / 置信度不达标 / 已发布 runbook 被反例推翻）。确定性裁决器只裁决**协调决策**（结构/约束/证据一致性），**根因真假由人最终裁决**；LLM 只提供候选解释、不担任法官；不决 → 升级给 IC（发言以 `Guidance` 节点入账本）。

**终止条件**：① 根因由 IC 确认且证据链闭合 → 话题关闭；② agent 预算耗尽 → 冻结为只读；③ 仲裁时间盒到 → 升级给人；④ 人宣布裁决 → 关闭；⑤ 已排除假设入反证清单——**绑定时间窗+系统版本+前提条件**，重开需新证据。

**防噪声闸门**：聊天不进事实层 · 操作指纹去重（同查询 single-flight，不同标签的重复查询也被压掉）· 预算（每 agent 每事故 token/step cap）· 时间盒 · 断路器（仲裁队列/冲突数/消耗异常 → 冻结或直通人）。

### 5.5 上下文管理

每个本地 agent 上下文有限，**不推全图**。上下文**动态检索**，围绕任务/时间窗/证据新颖度/风险，而非固定图距离：

| 内容 | 分发方式 |
|---|---|
| L0 事故卡（指纹/状态/IC/症状集） | 常驻，几 KB |
| 工作单元上下文（当前 question + 相关证据 + 反证清单） | 按认领推送，增量 |
| 历史与知识（相似事故/候选 runbook） | `query_knowledge` 拉取制 |
| 全量 IOM | **权限 + 预算 + 脱敏的门控按需查询**（不再绝对禁止本地 agent） |

配套：**context@vN 版本化**（变更只推 diff）；**结论隔离**（其他 agent 的结论只作为带置信度的假设呈现，永不作为事实注入——防级联幻觉）；**压缩**（低置信度/过期证据退役进账本，活跃上下文只留强证据）。

### 5.6 知识库治理（三级知识）

```
T1 认证 Runbook（事故后认证所得）——类型化+版本化，黄金知识
T2 因果知识图谱（跨事故学习）——症状→根因→修复边，血缘加权，用于指纹召回
T3 原始轨迹/案例库（证据所得）——append-only 账本，T1/T2 的 proof_trace 指向这里，可回放
```

- **runbook 生命周期**：`candidate（事故中）→ reviewed（静态/策略/历史replay）→ validated（测试环境/canary）→ certified（发布）→ revoked`。只有 `certified` 才在下次事故中自动执行，其余只作候选浮出。
- **失效驱动（非 TTL）**：失效由**依赖版本变化 / 拓扑 / API / 权限模型 / 组织策略 / 失败率 / 反例**触发重验；TTL 只作提醒。
- **反例回写**：已发布 runbook 实战失败 → 自动记为 refuting 证据、触发重验、生成"runbook 修复工单"。错误被知识库吃掉而不是丢失。

### 5.7 能力体系（Skill → Expert → Expert Group，借鉴 WorkBuddy）

平台不拥有 agent，但**编策 agent 的三级能力体系**：

- **Skill（技能包）**：领域 MCP 工具 + 提示词 + 护栏。按工作单元下发**最小能力集**（K8s 工作项 → kubectl 只读包；DB → SQL explain 包），读写分级，写工具永远走护栏 + 人审。
- **Expert（专家）**：Skill + 该领域的**经验**（蒸馏 runbook + 知识图谱）——"排障专家" = 某域能力 + 该域已验证知识，可被直接指派。
- **Expert Group（专家团）**：多个 Expert + 协作流程 = **事故响应工作图**（探索/验证/怀疑/执行角色）。**借鉴分层，不借鉴"全过程自主运行"**——专家团默认受 IC + PMA + 证据门控约束（§5.4），这是与 WorkBuddy 最激进的差异。
- **供应链治理**：skill pack **签名、锁版本、生成 SBOM、支持紧急撤销**；来源：平台内置 / 团队共享 / agent 自带，统一 manifest 声明 `requires_lease / permissions / safety_level`。
- **知识→技能闭环**（系统飞轮）：认证 runbook → 自动生成配套 skill 微包 → 下次命中同一 runbook 的 agent 自带全套工具直接执行。**知识生产能力，能力再生产知识。**

### 5.8 模型无关与成本路由

平台自身所有 LLM 调用（无头调查员 / 蒸馏器 / 仲裁候选生成）**模型无关**（混元/DeepSeek/GLM/Claude 等可切换），并支持 **`--model auto` 成本感知路由**：分类/去重/指纹用便宜小模型，深挖 RCA/runbook 生成用强模型。本地 agent 的模型由工程师自选（BYO），平台只路由自己的计算。

## 6. 接入：MCP 适配器「发言人」

本地 agent 唯一入口。Claude Code / Codex 均支持 MCP，适配器为薄层。

```
tools:
  incident.check_in
  incident.work_claim(question, scope, cost)   # 认领工作单元（咨询性租约）
  incident.register_operation(...)            # 查询前登记操作指纹（single-flight）
  incident.push_evidence(...)                 # 每步排查结果（带血缘）
  incident.get_context(incident_id)           # 上下文包：工作项 + 相关证据 + 反证清单
  incident.query_knowledge(症状指纹)           # 历史命中（只作候选）
  incident.propose(...)                       # 提案（带证据链，PMA 入口）
  incident.submit_arbitration(evidence_chain) # 仲裁轮次提交证据链
  incident.get_excluded()                     # 反证清单（绑定时间窗/版本/前提）
  incident.load_skill_pack(work_node)         # 按工作项领取最小能力集
  incident.propose_action(...)                # 提修复方案（走护栏，typed action）
resource:
  incident://<id>/context@vN                  # 只读上下文资源（版本化）
hooks（可选）:
  命令执行前后自动记录 → register_operation + push_evidence
```

平台同时内置**无头调查员**（LangGraph + Aurora 编排，复用开源积木，即"数字员工"），负责：首轮分诊、指纹匹配、无人时 7×24 兜底自主排查，连接企业知识库与告警/变更系统。**交互三模式**：`plan`（先拆解 + 与 IC 确认工作图再执行，默认用于写路径）/ `craft`（自主执行，仅用于读路径且理解充分的场景）/ `ask`（知识问答）。

**事故入口**：钉钉 / 飞书 / 企微 / Slack 告警 webhook 可直接创建事故并拉起无头调查员（IM 只作入口与通知，协同仍在平台完成）。

## 7. 可视化：指挥室 Incident Command View（P3）

| 视图 | 内容 |
|---|---|
| 事故总览 | 活跃事故列表 + 指纹 + 状态 + IC + 关联告警集 |
| **工作图** | 调查工作单元 DAG：谁在做哪个 question、成本/预算、进展、租约状态 |
| **因果图** | 症状→证据→假设→根因，实时生长 |
| **证据血缘图** | 每条证据的 Operation/数据源/独立性，重复与盲区一目了然 |
| **协同态势** | agent 活动流 + 无意重复热力图 + 受控冗余标记 |
| **协商视图** | 提案/仲裁流：谁提了什么、证据对比、协调裁决、升级给谁 |
| 生命周期时间线 | 告警→分诊→调查→候选→认证→修复→验证→复盘 |
| 知识面板 | 本次事故产出的候选/认证 runbook、去重数、历史命中 |
| **上下文飞轮** | 每次调查新增的事实如何充实共享上下文、加速下一个工作项（飞轮可视化） |

**差异化**：现有产品画"事故"，本设计画"人 × agent 的协同过程本身"。

## 8. 失败模式与治理

| 风险 | 对策 |
|---|---|
| 幻觉根因 | 证据门控 + 结论隔离 + 强类型动作（§5.3/§5.4/§5.5） |
| agent 死循环/token 爆炸 | step cap + 断路器 + supervisor 确定性编排（社区共识） |
| 无尽讨论/噪声 | 聊天不进事实层 + 操作指纹去重 + 预算 + 仲裁时间盒（§5.4） |
| 从众放大/级联幻觉 | **血缘独立性**（按数据源/采集链路算，不按 agent 数）+ 结论隔离（§5.4/§5.5） |
| 陈旧知识自动化 | **依赖失效驱动**重验，TTL 只作提醒（§5.6） |
| 越权/权限过大 | STS 最小权限 + 能力最小集 + 双人审批/职责分离（§5.7/§9） |
| prompt injection / 证据投毒 | 完整威胁模型 + proof 完整性（§9） |
| 审批疲劳/信息不足 | 审批信息充分性 + 双人审批 + 风险分级（§9） |
| 无法审计 | 证据总线 append-only，血缘 DAG 可回放 |
| agent 崩溃 / 晚到结果 | 租约超时释放 + 晚到结果标记 stale 不污染（§5.1） |

## 9. 安全与威胁模型（P4 前置条件）

> 不完成本层，不进入任何自动执行或自动生成 skill 的工作。

### 9.1 信任边界与三层安全模型

本地 agent → MCP 适配器 → 控制平面 → 客户侧 gateway → 环境执行桥，五段之间**零信任**：每跳最小授权 + 双向 TLS + 每动作独立鉴权。身份体系绑定**人-机-云**三层：用户身份、agent 身份、工具身份、云资源身份统一映射，所有动作不可抵赖签名。

安全整体按**三层模型**组织（借鉴 WorkBuddy 企业版）：

- **行为安全**：执行沙箱（云端沙箱 / gateway 容器隔离），动作 dry-run + 可回滚；
- **权限安全**：最小权限（STS 按事故临时授予）+ 能力最小集 + 双人审批/职责分离；
- **网络安全**：出站管控（客户侧 gateway 只出向白名单），数据分级驻留。

### 9.2 威胁清单与对策

| 威胁 | 对策 |
|---|---|
| prompt injection（恶意日志/恶意 runbook/恶意 MCP 输出） | 日志内容只作数据不作文本指令；外部内容一律按"未信任数据"标注；MCP 输出白名单化 |
| 证据投毒（proof_trace 篡改/截断/选择性提交） | 证据总线哈希链 + 签名；每条证据记录来源、时间窗、调用者、模型、父证据、内容摘要 |
| 审批-执行不一致（审的是语义动作，执行的是模板展开命令） | **审批对象 = 展开后最终动作**，dry-run 输出绑定审批内容 |
| 插件供应链（skill/adapter pack 即执行代码） | 签名 + 锁版本 + SBOM + 沙箱 + 紧急撤销（§5.7） |
| 多租户/跨客户知识泄漏 | 租户隔离 + **runbook 跨团队/跨客户学习显式开关**，默认关闭 |
| PII/密钥泄露 | 脱敏管道（密钥/手机号/token 正则+LLM 辅助），出侧上报前脱敏 |
| 数据驻留/删除权 | 数据分级：原始日志留在客户侧 gateway；控制平面只收脱敏摘要与结构化证据；保留期可配、删除权可执行 |

### 9.3 "数据不出客户网络"的诚实表述

控制平面收的是**脱敏摘要 + 结构化证据**（`Fact`/`Hypothesis`/操作指纹），**原始日志/原始命令输出留在客户侧 gateway**。证据要在控制平面完成协同与血缘，但敏感原始数据不跨境。

### 9.4 部署模式（企业不能假定恒有出向公网）

- **SaaS**：控制平面托管，客户侧 gateway 出向连接。
- **客户托管控制平面**：控制平面部署在客户内网，与 gateway 同域。
- **全离线**：控制平面 + gateway 全部内网部署，插件离线包签名安装。

### 9.5 平台自身韧性

- 平台自身 SLO、容量模型、灾备、可观测性（自举监控）；
- 控制平面故障 / 网络分区 / 监控系统故障时**降级策略**：降级为"纯本地排障 + 事后合并"，不阻塞止血；
- 事故聚合/拆分/合并/误关联与跨事故因果（告警→事故的 merge/split 规则）。
- **业务拓扑来源**：`Service` 业务语义从 CMDB/部署清单导入，冲突有裁决 owner。

### 9.6 企业管理后台（多租户治理面）

组织架构管理 · 成员授权控制 · 统一治理审计 · **成本管理**（token + 云 API 调用成本，对接 §5.8 模型路由）· 安全审计。目标：Agent 治理"从散装变统装"（借鉴 WorkBuddy 企业版）。

## 11. 环境接入与适配层（低成本接入）

### 11.1 核心立场

> **平台不接"云"，平台只讲有界的、版本化的 typed capability。每家新环境做的是"声明能力 + 填映射"，而不是"写一套实现"。** 目标不是"零成本接入"，而是**降低每次适配的必然成本**。

### 11.2 版本化 Capability Descriptor（替代封闭动词表）

每个环境声明一份版本化 descriptor，控制平面**按声明协商**能力（不假设封闭动词表）：

```
capability:
  resources: [ack.pod, ecs.instance, rds.instance, ...]   # 支持哪些资源类型
  queries:   [{verb: query_metrics, dialect: promql, idempotent: true, ...}]
  actions:   [{verb: rollout_restart, schema: {...}, idempotent: true,
               dry_run: true, rollback: true, max_scope: "{ns}/{deploy}",
               permission: change-window-gated}]
  data_residency: raw-logs-local-only
```

每个动作/查询必须声明：参数与返回值 schema · 幂等性 · dry-run 能力 · 回滚能力 · 最大作用域 · 权限与数据驻留要求。**`run_command` 不进入普通 capability**，仅作审计受限的兜底。

### 11.3 接入成熟度分级（不承诺"一天接入完整闭环"）

接入不是一次性事件，按能力逐级验收：

1. **只读观测**（告警 + 查询）→ 2. **资源身份与拓扑** → 3. **受控执行**（typed actions）→ 4. **验证与回滚** → 5. **安全合规与运维责任**。

每级通过 **connector conformance suite**（模拟服务 + 故障注入测试 + 兼容性矩阵）验收后才解锁下一级。

### 11.4 四档接入成本

| 档位 | 适用场景 | 做法 | 成本 |
|---|---|---|---|
| Tier 0 标准接入 | 有 OTEL + 标准告警 webhook + 只读查询 | 通用 connector + descriptor 声明 | 配置，~数天 |
| Tier 1 方言接入 | 已知平台（阿里云/AWS/Azure/K8s/Prometheus） | 预制 platform pack，只填端点+凭证+资源映射 | 填配置，~数天 |
| Tier 2 插件接入 | 私有云/独有 API | connector 插件实现 descriptor；平台其它能力白拿 | 1 插件，~周 |
| Tier 3 社区生态 | 任何后来者 | 插件市场，大概率命中已有 pack | 边际成本趋零 |

**按能力缺口实现，不按公司实现**：一家"Prometheus + K8s"公司无需新 connector；只有 CMDB 独特到需写码的，也只写拓扑一个模块。

### 11.5 标准协议吃掉大部分工作量

- **数据**：OTEL 只负责遥测交换；PromQL / SLS / CloudWatch / CMDB 各自做正式 connector（方言不消失，被 descriptor 封装）。
- **事件**：Prometheus Alertmanager / 标准 webhook JSON（阿里云告警 → EventBridge 也走 webhook）。
- **执行**：优先调用企业已有自动化系统（Ansible/Argo/变更平台），**不建立通用 shell 后门**；兜底才用受限命令模板 + 执行桥。

### 11.6 部署形态与数据驻留

- 客户侧 **gateway** 部署在客户 VPC 内（Helm/Terraform 一键），负责查询、脱敏、资源解析、权限、执行；**原始数据本地检索与摘要**。
- **护栏不因接入方而异**：无论哪个 connector 执行，都走平台同一套护栏引擎；descriptor 声明 `permission / 变更窗口策略`。
- **凭证最小化**：STS 按事故临时授予、只覆盖涉事实体，每环境独立。

### 11.7 生态飞轮

开源 → 头部云 pack 免费贡献 → 插件市场 → 新公司多数直接命中已有 pack → "来一家实现一家"的问题被结构性消灭。**Pack 必须签名、锁版本、生成 SBOM、支持紧急撤销。**

## 13. 成功指标

**主指标**（反映真实价值，不是口号）：
- **无意重复率**：single-flight 压掉的重复查询占比（P0）。
- **有效独立验证覆盖率**：高风险结论中，被 ≥2 个独立数据源验证的比例（P0）。
- **单位工具成本的信息增益**：每个 Operation 新增的已确认事实/排除项（P1）。
- **错误排除率**：被误排除的假设比例（P1）。
- **决策延迟**：从告警到 IC 做出根因判断/止血决策的时间分位数（P0-P3）。
- **二次命中率 / 冷启动率**：相似事故命中候选 runbook 的比例（P1）。
- **MTTR**（Mean Time To Resolve）分位数（P2/P3）。

**负向指标**（必须跟踪，防止指标失真）：
- 误根因率 · 误修复率 · 漏报率 · 审批质量（疲劳/信息不足）· 知识污染率（错误 runbook 被采纳的比例）。

**评测机制**：离线评测集 + **shadow mode**（只观察不执行）+ 对照组（共享 Slack + 人工 IC vs OpsHive），满足上线门槛才放量。
